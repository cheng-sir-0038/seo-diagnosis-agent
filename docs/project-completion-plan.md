# 多领域 Agent 工作台优化计划

## 目标与范围

把现有项目完善到可以由小团队试运行。用户从首页用自然语言、网址或资料发起任务，在原对话补充信息并继续执行，从任务列表找回进度，从执行详情查看结果依据。维护者能通过运行中心定位失败的步骤，判断问题能否重试，并确认重试结果。保留现有 React、FastAPI、LangGraph 和 PostgreSQL 架构。

计划以当前检出版本 `de72db6` 为基线，该版本已包含对话续跑时保留已提交答案的改动。Python 3.11.18 已在审查环境安装，前端类型检查此前通过，后端测试和前端 Vitest 仍需建立可运行的基线。三张原型作为交互参考。平台管理能力按试用场景安排，公开或跨团队部署另设上线条件。

SEO／GEO 的交付范围止于读取可访问的页面、诊断问题、提供依据和可执行的修改建议。站点负责人在自己的 CMS、代码仓库或部署系统实施。工作台可在修改后的页面可访问时做只读复查，给出观察到的差异。外部站点写入、修复和上线均不纳入本期范围。

仓库中名为「发布」的 [HTML 适配器](../src/seo_agent/publishing/html_site.py)写入服务进程可访问的目录，[示例配置](../.env.example)使用本地路径。确认接口请求目标 URL 检查可达性。这套能力不提供第三方站点的编辑权限，本期无需把它接入 SEO 诊断流程。

## 阶段 0 — 建立可重复验证的开发环境

用仓库锁文件在干净环境安装前后端依赖，确认 Vitest 能加载目标平台的原生依赖。准备测试 PostgreSQL，核对数据库初始化路径、健康检查和配置示例。先跑前端类型检查、构建与 Vitest，再跑后端 pytest，记录明确依赖真实服务或凭据的用例。将确定性的检查接入 CI，使用固定样例和工具替身验证工作流。真实供应商请求单独做冒烟验证。

验收时，从干净检出按 README 可以启动应用并复现测试结果。形成一份基线记录，标明测试通过、失败和需要外部条件的部分。把对话续跑的现有差异作为独立变更评审，确认测试结果后再作为后续开发基线。

## 阶段 1 — 先打通首页、任务和对话的完整流程

以服务端任务状态为准，明确任务 ID、运行 ID、补充请求 ID 和事件序号各自的用途。统一首页、任务列表、对话标题和运行中心的状态映射，区分排队、运行、等待补充、完成、部分完成、失败和取消。列表支持回到指定任务和待补充位置。首页保留五个业务入口和真实最近任务，统一导航与窄屏布局，补齐空态、加载态和错误后的重试入口。任务进度先展示可验证的阶段或状态，具备可靠分母的流程再显示百分比。

把等待补充作为一条完整链路来验证。提交请求能关联当前补充问题，重复提交或响应丢失后可以核对是否已接收，已接收的答案不会再次触发流程。区分「重新连接当前运行」和「从检查点恢复」。对话保留已有结果，执行详情按实际事件展示参与的 Agent、工具状态、引用和附件。失败或取消后的可用结果仍可回看。

验收以两条演示路径为准。第一条从首页提交网址，得到按优先级排列的 SEO 诊断、页面证据和可交给站点负责人的修改建议，再从最近任务找回同一次运行。第二条从首页发起缺少会议地点的商旅任务，在原对话补充，分别验证刷新、断线、重复提交和切换会话后的恢复，确认同一补充请求只产生一次有效续跑。两条路径均检查宽屏与窄屏交互。

主要入口为 [首页](../frontend/src/components/WorkspaceHome.tsx)、[任务列表](../frontend/src/components/WorkspaceActivity.tsx)、[对话](../frontend/src/pages/ChatPage.tsx)和[现有集成用例](../frontend/src/__tests__/ChatSeoAgentIntegration.test.tsx)。

## 阶段 2 — 修复定时扫描的停用与重试

定时扫描在同一事务的行锁下检查计划是否启用或归档，并保留手动触发规则。用调度触发时刻生成幂等键和 `scheduled_at`，独立记录实际启动时刻。停用后已注册的回调应被拒绝启动。同一调度时段的重试应返回既有运行或明确的跳过结果。

验收覆盖暂停后旧回调触发、同一时段重复投递和扫描重叠。确认停用后无新扫描启动，重复投递不增加运行记录，已启动的扫描按现有规则结束。本阶段可与阶段 1 并行，验收通过后再启用试运行环境的定时扫描。

主要入口为[调度回调](../src/seo_agent/automation/schedules.py)和[扫描启动服务](../src/seo_agent/opportunities/service.py)。

## 阶段 3 — 把运行中心做成可用的排查工具

将时间范围、状态、搜索、排序和分页移到后端。仪表盘按同一时间窗口计算应用运行量、失败运行量、工具调用量和等待补充运行量。默认用应用运行作为任务计数单位，Trace 作为排查记录。等待补充按所选窗口内进入该状态且截至窗口结束仍未解决的运行计数。比较上一等长窗口并生成趋势序列，页面注明口径与时区。

保持运行详情中的调用树、事件和输入输出，打通对话到对应 Trace、Trace 返回原会话的链接。确认模型与工具明细可定位到具体步骤，错误定位和问题状态变更可追踪。对附件内容、个人信息和凭据设置展示边界，观测日志默认使用经过脱敏的摘要，按试运行权限控制详情访问。

验收使用固定数据集验证跨页统计、时区边界、前后窗口对比和同一次运行关联多个 Trace 的计数。至少演练供应商失败、等待补充和恢复成功三种运行，维护者能在运行中心定位最近的出错步骤并跳回关联对话。

主要入口为[观测页](../frontend/src/pages/ObservabilityPage.tsx)和[观测 API](../src/api/routes/observability.py)。

## 阶段 4 — 验证五类业务并准备试运行

每个业务入口定一条标准任务和一条异常任务，固定输入、预期结构、可用数据源和降级表现。SEO／GEO 在可控的样例站点验证诊断交付。初次检查记录 URL、采集时间、问题证据、优先级、修改建议和验证方法。由测试人员修改样例页面，再提交同一 URL 复查，区分问题已消失、仍存在和无法验证，并保留前后证据。外部站点若尚未由负责人修改，任务状态显示「诊断已完成」或「待复查」，不得标为「已修复」。医疗健康验证公开资料查询及引用，使用合成样例验证复诊资料整理。学习教育验证逐题作答、解释及学习计划。商旅行程验证地点或日期缺失时的澄清、候选比较和跳转。购物采购验证预算、数量和报价时间能追溯到来源。外部数据缺失、过期或超时要能区分，界面明确显示当前能交付的部分。

试运行前准备配置检查、数据库备份与恢复、部署回滚、运行排查和供应商故障处理说明。小团队共享部署需要身份认证、会话与附件的访问隔离、管理权限和操作审计。告警先覆盖持续失败、队列积压或调度异常等能采取行动的情况。应用管理、独立权限后台、供应商下单和复杂告警规则按试运行需求立项。商旅和采购的真实交易需要供应商能力和用户确认，作为独立验收项。

验收要求五个入口各自通过标准与异常场景，完成一次备份恢复和一次回滚演练，并确认试运行环境的权限边界。试运行记录任务完成率、等待补充后继续率和恢复成功率，作为下一轮优化依据。对外或跨团队开放前，额外完成租户隔离、配额限流和数据保留验证。

## 实施顺序与工作量

| 阶段 | 交付件 | 粗估工程人日 | 依赖 |
| --- | --- | --- | --- |
| 0 | 可复现的测试基线和 CI | 2–3 | 依赖安装、测试 PostgreSQL |
| 1 | 首页到任务执行、补充与恢复 | 5–8 | 阶段 0，现有对话变更评审 |
| 2 | 停用调度和幂等重试 | 1–3 | 阶段 0，可与阶段 1 并行 |
| 3 | 正确的时段指标和可定位的 Trace | 4–6 | 阶段 0，阶段 1 的运行状态约定 |
| 4 | 五类业务验收与小团队试运行交接 | 5–8 | 阶段 1–3，试用环境与数据源配置 |

合计粗估 17–28 工程人日，假设现有架构和供应商接口可复用，包含增量实现、回归测试与文档。共享部署若需新建认证和数据隔离，或供应商接口需要新增授权，单独估时。完成阶段 0 后按实际测试差异更新估算。首批交付以可重复的测试基线、SEO 诊断交付、商旅补充续跑和定时扫描可靠性为主。
